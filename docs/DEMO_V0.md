## 1. `worldRevision` — 貫穿全部八個 Issue 的核心機制

這是 Issue 群裡最重要的架構發明，而且它**不在既有的 `ENGINE_BOUNDARY.md` 裡**，已補。

它是一個版本 token，用途是**讓過期的分析結果無法造成傷害**：

| 場合 | 規則 |
|---|---|
| 失效事件 | 過期 `worldRevision` 的事件被拒絕（#2） |
| 應力圖 | 過期版本的掃描資料不得顯示成最新結果（#2、#7） |
| 掉落 member | 攜帶產生它的 `worldRevision`，避免重複生成或舊事件覆蓋（#3） |
| 損傷紀錄 | 記錄哪一次世界／分析版本造成損傷；重複或過期事件不重複累加（#4） |
| 重新安裝 | 建立**新** `worldRevision`，重新分析成功才恢復承載（#3、#4） |
| 帶載切割 | topology change 產生新 `worldRevision` 並立即送承諾分析（#8） |

**這解決了一個我在 D-007 兩軌設計裡沒處理的問題**：顯示軌可以 stale，但 stale 到什麼程度算過期？`worldRevision` 給出答案——**只要世界版本變了，舊結果就是過期的，而不是「舊但可用」**。

### 對兩軌的精確化

- `DISPLAY` 軌結果可即時更新，但**必須明示「分析中／過期」**
- **只有 `COMMIT` 軌能觸發失效**
- 過期不是降級顯示，是**明確標示狀態**

## 2. 失效交接邊界（#2）

```
結構求解器 → 失效事件 → 視覺／物理轉接器
```

三條硬規則：

1. **結構求解器是唯一決定「是否失效、何處失效、失效模式」的來源**
2. **剛體系統只接管已斷開的構件，不反過來決定結構強度**
3. **物理 Mod 只負責壓碎後的視覺動畫**

第一版採**單向交接**：一旦區域交給剛體／碎裂系統，就不再回到同一次 FEA 模型。

統一事件：`FRACTURE`、`CRUSHING`，攜帶 `worldRevision`、位置、法向／方向、嚴重度、受影響構件。

> 這個邊界讓未來更換物理 Mod 不必改寫結構求解器。

**這是 `CLAUDE.md` 「算的歸算，演的歸演」的精確版本**，而且比原則更嚴格——它指定了事件形狀與單向性。

### 兩種失效的呈現差異

| | 斷裂 | 壓碎 |
|---|---|---|
| 序列 | 裂口張開 → 分離 → 倒下 → 切換剛體 → 墜落翻滾至靜止 | 判定區域 → 交給物理 Mod → 碎裂動畫 |
| 產物 | **持久的剛體 member**（有傷害、可破壞、可重裝） | **純視覺碎片** |
| 碎片 | — | **不造成傷害、不成為持久物件、不可回收、不污染存檔** |

## 3. 防複製設計（#5、#8）⭐

Issue 群裡最漂亮的一組設計，值得單獨提。

**關鍵區分**：

- **倒塌／壓碎瞬間** → 外部物理 Mod 的飛散碎片是**純視覺**，不可撿取
- **事後拆除作業** → 玩家執行敲除，**伺服器才結算**可回收碎料

> 這樣能避免把大量動畫碎片變成持久實體，同時保留材料回收玩法。

配套的三條守則：

1. **可回收量由實際敲除進度與剩餘混凝土量決定，不根據動畫粒子數量**
2. **結算由伺服器權威處理**，避免客戶端重播動畫複製材料
3. 切割／熔煉必須帶**唯一 transaction ID**，重試或伺服器重啟不得重複產生材料

質量守恆（#8）：
```
子 member A 質量 + 子 member B 質量 + 切割損耗 = 父 member 質量
```
且「材料、斷面與長度決定可熔煉質量；**不能按照視覺物件數量給產物**」。

## 4. 損傷是身分的一部分（#4）⭐

> 損傷是 member 身分的一部分，**不是一次性的動畫旗標**。

明確拒絕單一耐久度：

> **不建議只保存一個通用的「耐久度百分比」**，因為相同百分比無法區分裂紋、屈曲與塑性彎曲的不同力學後果。

損傷模式：`FRACTURE` / `PLASTIC_BEND` / `BUCKLING` / `IMPACT` / `CRUSHING`。

**分層很乾淨**：
- Java／Minecraft 層**只保存事實與呈現**（`DamageRecord[]`：模式、位置、方向、嚴重度、來源事件、時間）
- **結構引擎負責把損傷紀錄轉成剛度、強度、有效斷面或失效準則的變化**

這與 `ENGINE_BOUNDARY.md` 的分工完全一致——遊戲側不發明力學折減公式。

## 5. 混凝土不可修補（#5）

> 不允許透過補丁或一般修補，把原受損構件的強度恢復。

力學理由誠實：**不模擬任意裂縫形狀下的混凝土殘餘剛度；失效後改用離散狀態。**

這是一個「用產品規則迴避難解力學」的漂亮例子——與其做一個不可信的殘餘強度模型，不如規定它不可修補，然後把玩法建在敲除與回收上。

狀態機：
```
INTACT_COMPOSITE → IRRECOVERABLY_DAMAGED → CHIPPING → EXPOSED_STEEL → RECONNECTED / DISMANTLED
```

**敲除後原 RC／SRC 複合斷面失效，暴露鋼材只能按自身斷面、連接與損傷承載。** 這與 `ARCHSIM_PORT.md` §1 的 `Skeleton / Cured` 兩階段是同一個機制的反向——養護是 Skeleton→Cured，敲除是 Cured→Skeleton（但帶著損傷）。

## 6. 檢查不是門檻（#6、#7）

> 檢查不是強制關卡；玩家可以直接冒險使用，也可用應力眼鏡診斷或截除較差區段。

> 應力眼鏡是世界內的診斷工具，**不是強制通關畫面**。它提供資訊與警告，但**不替玩家禁止施工**。

驗收條款：**未使用應力眼鏡不會阻止施工，但風險仍反映在分析結果。**

這條與教育目標一致（`CLAUDE.md` 的 Productive Failure）——**讓玩家有能力做出糟糕的決定，然後看到後果**。

### 掃描模式

| 模式 | 內容 | 版本 |
|---|---|---|
| `UTILIZATION` | D/C 與利用率，安全／接近極限／失效 | v0 必要 |
| `DAMAGE` | 裂紋、屈曲、永久彎曲、撞擊的位置與嚴重度 | v0 必要 |
| `MATERIAL` | 材料等級、斷面 token、混凝土批次／齡期、回收來源、既有損傷 | v0 必要 |

| `CONSTRUCTION` | 接頭、模板、養護、臨時支撐狀態 | 後續 |

## 7. ✅ 與 D-010 的架構衝突（已裁決為 B — D-011）

`DECISIONS.md` D-010 規定：**member 由鋼筋／鋼骨的共線 run 擷取**——也就是 member 是**從方塊拓撲推導出來的**，每次重新擷取。

但 Issue #3、#4、#6、#8 要求 member 有**持久身分**：

- `memberId` 與來源結構（#3）
- `DamageRecord[]` 跟著 member 走，掉落、存檔、重裝都不遺失（#4）
- 新複合構件取得**新的 member identity**，並保存 recycled lineage（#6）
- 切割產生**兩個具有新 identity 的子 member**，父 member **原子性退役**（#8）

**這兩件事不能同時成立而不做設計。** 純推導模型下：

- member 沒有身分，只有「這輪擷取出來的第 N 根」
- 損傷無處可掛
- 切割無意義（把方塊挖掉一格，重新擷取自然就變兩根，但沒有 lineage、沒有 transaction、沒有質量守恆）

### 三個選項

| 選項 | 做法 | 代價 |
|---|---|---|
| **A · 損傷掛在方塊上** | member 仍純推導，`DamageRecord` 以方塊座標為 key 儲存，擷取時聚合到 member | 切割的 lineage 與質量守恆難做；「member 身分」是幻覺 |
| **B · member 是持久物件** | member 有 registry 與穩定 ID，方塊只是它的視覺表現 | 與 D-010 的「拆掉混凝土拓撲不變」檢驗相容，但自由模式（推導）要能產生穩定 ID |
| **C · 混合** | 擷取產生 member，另有 identity registry 在多次擷取間維持穩定 ID（以幾何指紋比對） | 最複雜，但兩邊都成立 |

**傾向 B。** 理由：#8 的質量守恆與 transaction 語意需要一個可以「原子性退役」的物件，那必須是持久實體。而 D-010 的核心洞見（結構模型來自骨不是肉）在 B 之下仍然成立——**鋼筋/鋼骨的放置決定 member 何時誕生，但誕生之後它有自己的身分**。

自由模式（`DECISIONS.md` D-003 的長期目標）在 B 之下也做得到：推導只負責**建立**與**更新** member，不負責每幀重新發明它們。

**已裁決**（D-011）。這個決定影響持久化格式、擷取實作、切割與回收的全部語意，而且**改起來很貴**。
