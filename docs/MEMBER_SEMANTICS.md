# 構件語意

**狀態：設計草稿。** 本檔記錄推導與已達成的判斷，未決問題明確標示。定案後相關條目移入 `DECISIONS.md`。

移植清冊把「構件擷取」列為最大缺口（`PORTING_INVENTORY.md` §G-1）：前身設計**只有方塊，沒有構件**，從方塊集合到 6-DOF 梁元的映射完全不存在。這份文件處理那個缺口。

---

## 1. 一個方塊不是一根桿

樑理論要求細長比。Euler-Bernoulli 需要 `L/h ≳ 10`，Timoshenko 勉強到 `L/h ≳ 3`。

一個 1m×1m×1m 的方塊 `L/h = 1`——那是實體塊，平截面假設完全不成立。**「一方塊 = 一根 member」在力學上是錯的。**

正確的映射是**共線 run → 一根 member**：

```
10 個方塊疊成的柱  →  一根 10 m 長、1 m 見方外廓的 member，L/h = 10  ✓
單一孤立方塊跨越缺口 →  L/h = 1，樑理論失效       ✗
```

這是好消息：run-length 抽取是便宜的線性掃描，不是形狀語意辨識。

---

## 2. 玩法即離散化的合法性條件 ⭐

「從任意方塊堆反推哪些是柱、哪些是梁」是形狀語意問題不是力學問題，三個既有引擎倉庫都沒有解，而且它是本專案原本最大的未解問題。

**解法是不要反推，讓玩家用材料宣告。**

| 玩家放的東西 | 力學上是什麼 |
|---|---|
| 鋼骨、鋼筋、繩索 | 桿件（member） |
| 架模板 → 灌漿 → 養護 | 板殼（shell） |
| 其他方塊 | 非結構 |

這不是繞過問題，是**消滅問題**。而且它剛好對應真實工程——結構圖說本來就標明構件，工程師不從照片反推。

**副作用是好的**：工法玩法與離散化合法性成為同一件事。玩家「照工序蓋」不只是遊戲規則，同時保證了模型是可解的。

**代價（明確接受，記於 D-003）**：放棄「對任意原版方塊建築出應力」。應力眼鏡只作用於用結構材料蓋的東西；原版方塊最多得到連通性層級的回饋。

## 3. 斷面與方塊尺寸解耦

方塊是**斷面的載體**，不是斷面本身。

反例白紙黑字寫在前身設計裡（Node 報告 C1-3）：

```
● blockSectionModulus ── FLOAT [默認 1/6]
```

`1/6` 正是邊長 1 的正方形斷面模數 `b·h²/6`——「一格 = 1m×1m 實心斷面」。

**後果**：1m 見方的實心鋼柱在真實工程裡是誇張的巨柱，D/C 恆為 0.01，任何結構都不會失效，遊戲性歸零。

**機制已經存在**：Node 報告 `B3-1 ShapeSelector` 從 10³ 體素造型自動算出 `A / Ix / Iy / Wx / Wy`，`B3-2 CustomShape` 有內嵌體素編輯器。要補的是：

- `Iz`、扭轉常數 `J`
- 剪力面積 `Av,y / Av,z`（Timoshenko 需要）
- 塑性斷面模數 `Zx / Zy`
- **斷面主軸方向 / local axis rotation** — 一根 I 型梁繞自身軸轉 90° 是完全不同的結構，前身設計完全沒有方向資訊（`BlockState` 的 facing 從未被用於物理）

**單位宣告**：一個方塊 = **1 m 長度** × 由 voxel grid 決定的斷面。這條「一格 = 1 公尺」在前身文件裡從未被明確寫下，卻是所有換算的前提。

## 4. 接合語意

前身設計裡「接合」= 方塊相鄰（26-conn 或 6-conn），**完全沒有剛接／鉸接的概念**。而剛接與鉸接的差別在靜不定結構裡決定了整個內力分佈。

### 4.1 `RC_NODE` 的新語意

`RC_NODE` 在前身是「鋼筋 + 混凝土融合後的複合材料方塊」，那個融合公式被審核報告判定「與變換截面法理論差距 10 倍以上」。

**在 FEA 下它最自然的語意是「剛性節點」**——現澆 RC 節點本來就是剛接的典型。這個重新詮釋同時解決了兩件事：保留了 BlockType 的語意，並補上了缺失的接合概念。

### 4.2 鋼骨：焊接前後不同 ⭐

這一條直接取自 ArchSim 已實作的 Weld 模式，是**遊戲性最強的一個瞬間**：

```
鋼骨生成時    →  兩端釋放彎矩（螺栓裸框架 ≈ 鉸接）
玩家焊接      →  改寫 release set 為全固接
                 →  踢一次 solve
                 →  熱圖立刻顯示彎矩重分配
```

玩家能**親眼看見**「把接頭焊死讓彎矩重新分配」。這是純量場永遠做不到的教學瞬間，因為它需要轉動自由度。

### 4.3 需要的資料模型

- member end release：釋放某端的 `My` / `Mz` / `T`（FrameCore 的 `Member::release[12]` + 靜態凝聚）
- 預設規則未決（見 §7）

## 5. 支承語意

前身的「支承」是布林 `isAnchored` + 「碰到 `y ≤ minBuildHeight+1` 或 AnchorBlock」，且**任何一個節點碰地就整個連通分量算穩定**——完全沒有 ΣF=0 / ΣM=0。

FEA 需要的是**每個受約束節點的 6 個自由度各自 fixed/free**。

未決問題見 §7。但有一條現在就能定：**支承不足時剛度矩陣奇異，Cholesky 會失敗。** 這是前身完全沒有的失敗模式，需要對應的玩家回饋——不是「計算逾時」，而是「你的結構是機構，不是結構」，並指出哪個節點缺約束。

## 6. 反向映射（解完之後）

前身的 `ResultApplicator` 吃 `Map<座標, float>`。FEA 的輸出結構完全不同：

```
需要：Map<memberId, MemberForces>        // N, Vy, Vz, T, My, Mz，沿桿取樣
      Map<memberId, Set<BlockPos>>       // 回寫索引，供渲染與坍塌
      Map<panelId, ShellResultants>      // 上下層各 5 點應力
```

**wire 上要多帶一個欄位：主導失效模式**（`AXIAL` / `BENDING` / `SHEAR` / `TORSION` / `COMBINED`）。

前身的每方塊純量只能上色。有了主導模式，玩家能知道「這根柱子不是被壓垮的，是被彎垮的」——**這是新增能力，舊設計裡不會有，重寫時要主動放進去**（記於 `ENGINE_BOUNDARY.md`）。

## 7. 擷取規則（已定案）

**核心：結構模型來自「骨」不是來自「肉」。**

鋼筋與鋼骨定義 member，模板定義 shell，混凝土兩者都不定義——它只改變外觀與斷面性質。

這與真實 RC 完全一致：配筋圖就是結構模型，混凝土是受壓元件與保護層。

### 7.1 分類判定

| 玩家放的東西 | 產生什麼 |
|---|---|
| 鋼筋、鋼骨 | **member**（6-DOF 梁元） |
| 模板圍出的**平面**區域 | **MITC4 shell facet** |
| 模板圍出的**線狀**區域 | member 的混凝土外包（複合斷面） |
| 澆置的混凝土 | 不產生任何元素。改變既有 member 的斷面與既有 shell 的厚度 |
| 其他 | 非結構 |

### 7.2 Q1 · member 的邊界 — 由鋼筋/鋼骨的接法決定

一根 member = 一段連續同向、同材料的鋼筋或鋼骨 run。**混凝土不參與分段**——把柱子外面的混凝土拆掉，member 拓撲不變。

### 7.3 Q2 · T 型交會 — 打斷，共用節點

玩家把兩根鋼骨焊在一起，或把兩束鋼筋捆在一起。**力學語意都是「兩根接在一起」**——兩根 member 共用一個節點，不是一根彎折的 member。

L 型轉角同理。

### 7.4 Q3 · 節點合併容差 — 零容差，整數座標

> **決定：不設容差。兩根 member 共用節點的充要條件是整數座標完全相等。**

具體規則：

1. **節點 = 被兩個以上 run 共用的方塊**（L 型與 T 型交會的那一格自然屬於兩個 run）
2. **或兩個 run 的端點方塊面相鄰**（對接）
3. **對角接觸不構成連接** — 只在角或邊相碰的兩個方塊不傳力
4. **並排平行的兩根 run 不連接** — 相鄰不等於接合

理由：整數格點給零浮點歧義（前身 `tectonic/lattice` 用的就是這條：「int32 座標、拓撲判定零浮點誤差」）。任何容差都引入歧義，而歧義破壞決定論——決定論是多人同步的前提。

規則 3 順帶正式殺掉 26-connectivity 作為連接概念（`PORTING_INVENTORY.md` §B-4），**但仍允許對角 run 當斜撐**：run 的成員資格由玩家的放置行為定義，不由鄰接關係推導。

### 7.5 Q4 · 斷面是 member 層級屬性

因為 member 由鋼筋/鋼骨拓撲決定、混凝土是外包，斷面自然是 member 層級的：`鋼骨斷面` + `混凝土外包` → 變換截面法算出複合斷面。

一根 member 中間斷面變化 → 在變化處打斷成兩根。

### 7.6 Q5 · 接合剛性由**接法**決定，不由材料

| 接法 | 接合狀態 | 力學 |
|---|---|---|
| 鋼骨**未焊接**（螺栓裸框架） | 鉸接 | 兩端釋放 `My` / `Mz` |
| 鋼骨**螺栓** | 鉸接 | 端彎矩釋放（顯式動詞，不只是預設態） |
| 鋼骨**焊接** | 剛接 | 全固接（`Release` 全 false） |
| 鋼筋**綁紮** | **定位，不傳彎矩** | 綁紮鐵絲不是結構連接 |
| 鋼筋綁紮 + **澆置養護完成** | 剛接（`RC_NODE`） | 剛性來自混凝土節點，不是鐵絲 |

**最後兩列是本專案最漂亮的一課，而且力學上是真的：** 綁鋼筋只是把鋼筋固定在正確位置，RC 節點的剛性來自澆置後的混凝土。玩家會親眼看到——綁完鋼筋結構還是軟的，澆置養護完成的那一刻彎矩才重新分配。

## 8. 兩種建造模式

| 模式 | 擷取方式 | 狀態 |
|---|---|---|
| **建築模式** | 鋼筋/鋼骨 → member；模板 → shell。**由結構角色宣告** | v1 出貨 |
| **自由模式** | 單方塊，由材料擷取 | **最終目標，非降級路徑** |

### ⚠️ 重要：自由模式不是次等公民

**建築模式是技術不足時的過渡，不是產品願景。**

用工法語言把「玩家必須先宣告結構角色」這個技術限制包裝成遊戲設計——這個包裝是**誠實的**（真實工程本來就這樣蓋，結構圖說本來就標明構件），而且它讓 v1 可以出貨。但它不能變成永久的藉口。

**長期目標是：玩家隨便蓋，演算法自己搞定，而且是全功能不是降級。**

那需要解掉「從任意方塊堆反推結構角色」——也就是形狀語意問題。**這個問題沒有消失，只是被排序了。** 記在這裡以免被「建築模式很優雅」的敘事掩蓋掉。

### 對架構的立即影響

既然自由模式最終要全功能，那麼：

1. **引擎邊界不能假設「玩家已宣告」**（`ENGINE_BOUNDARY.md` 的上行訊息帶 `結構角色` 欄位，未來要允許它為 `UNKNOWN` 由引擎推導）
2. **不要把宣告寫進持久化格式的必填欄位**——藍圖存的應該是幾何 + 材料，結構角色可重算
3. **構件擷取的實作要留一個 pluggable 的 strategy 介面**：`DeclaredExtractor`（v1）與未來的 `InferredExtractor` 共用同一個輸出契約

這三條的成本很低（現在做），但事後補很貴。

## 9. 三個補充（設計推論，非玩家指示）

### 9.1 混凝土不只變強，它先變重 ⚠️

「澆注只是外觀跟變強」在**成品狀態**成立。但施工過程中順序是相反的：

```
澆置       →  濕混凝土是純荷載，強度為零
養護中     →  強度隨對數曲線成長，荷載不變
養護完成   →  才開始貢獻斷面強度
```

**濕混凝土在成為強度之前，先是荷載。** 而承接這個荷載的正是模板與臨時支撐——這就是 §8.1 那一課的核心，也是真實工地最常見的倒塌原因。

這一點必須進模型：`POUR` 階段的 self-weight 要立刻生效，`strengthPercent` 要跟著養護曲線走。

### 9.2 模板有兩個角色，第二個在拆模後還在

| 角色 | 期間 |
|---|---|
| (a) 臨時支承 — 承接濕混凝土自重 | `POUR` → `CURE` |
| (b) **shell 元素的幾何宣告** | **永久** |

角色 (b) 必須在拆模後保留，否則拆完模牆就從模型裡消失了。

實作上：模板方塊被移除時，它宣告的 shell facet 不移除——移除的是那個臨時支承 BC。**拆模 = 移除支承 + 以當時的 `strengthPercent` 重解。**

### 9.3 素混凝土（無鋼筋）怎麼辦

若 member 由鋼筋/鋼骨定義，那麼一根沒有配筋的混凝土柱就**沒有 member**，不會被分析。

提議規則（待確認）：**模板圍出的線狀澆置區域，即使沒有鋼筋，也產生一根純混凝土斷面的 member。** 這剛好對應真實工程的柱模 vs 牆模/樓板模之分，也讓「素混凝土」這個既有材料仍有意義（抗壓可以、抗拉很差 → 玩家會學到為什麼需要配筋）。

### Q10 已答 · 多人 = 權威流重放

`tectonic2/CHARTER.md` 修正案 #4 A4-2 是唯一直接回答這題的既有資料：

> 北極星的多人語意 = **權威流重放（authoritative-stream replay）**：一條權威 solver 流產生帳，客戶端**重放流、不各自重算**。

配合 `tectonic/CHARTER.md` 的物理語意條款：力學核決定「誰壞、何時壞」，**碎片為純視覺層**；**server-authoritative（免 bitwise，GPU 可自由用）**；**結構 tick 可低於渲染幀率（客戶端插值）**。

對本專案的意涵：

| 項目 | 決定 |
|---|---|
| 誰來解 | **server 單一權威** |
| client 做什麼 | 收 replay stream + 插值，**不重算** |
| 碎片/粒子 | 純客戶端演出（呼應「算的歸算，演的歸演」） |
| 結構 tick | 與 render tick 解耦 |
| bitwise 決定論 | **不需要**——server-authoritative 就免了 |

⚠️ **pre-signed 條款**（照抄）：若 replay 模型改為客戶端重算，bitwise 決定論即成強制紅線，須先修這條決策。

配套的 LOD 規則取自 `教學/07`：**取所有玩家到 island 中心的最小距離**——只要有一個玩家靠近，該 island 就獲得高精度。

## 8. 相關的設計判斷（從討論中帶過來）

這些不屬於構件語意，但屬於同一批推導，記在這裡以免遺失。

### 8.1 模板是整個施工模組唯一真正需要 FEA 的地方

前身的模板只是 allowedBlocks 白名單，不承受任何荷載。

**正確做法**：模板在 `POUR → CURE` 期間作為**臨時支承**進入模型，濕混凝土自重由模板傳到下層。拆模 = 移除臨時支承 + 以當時的 `strengthPercent` 重解。

養護未完成就拆模 → 該構件失效。**這是教育價值最高的一課**，而且它需要真實的結構模型才成立——狀態機做不到。

### 8.2 建築尺度不需要增量求解

單棟建築約 2k–20k DOF。15,360 DOF 的完整管線實測約 108 ms。丟到 worker thread，玩家放方塊、兩三個 tick 後熱圖更新——建造遊戲裡完全可接受。

整套 Woodbury / LiveSession / stale 迭代機制存在的理由是 100k–1M DOF 的世界尺度。**我們不在那個尺度。**

切分：**建造時可以慢**（加節點 → 全量重分解，async）；**崩塌時要即時**（開關既有構件 → 精確 Woodbury，毫秒級）。詳見 D-008。

### 8.3 快照層是可以直接搬的架構資產

前身的 `RWorldSnapshot / WorldSnapshotBuilder / ResultApplicator` 三段式——主線程擷取不可變快照 → 異步純 Java 計算 → 主線程回寫——與 FrameCore 完全相容，而且它是唯一能讓 §8.2 的「全量重分解 async 跑」成立的架構。**直接搬。**

### 8.4 效能數字的口徑陷阱

引用 Tectonic 的效能數字時要注意：`400,896 DOF / 33.18 ms` 那個數字是 **u-only**（`lazyForces=true, lazyReactions=true`），**不含構件內力回收、不含反力、不含 D/C 著色**——而應力眼鏡要的正是那一層。

好消息是回收很便宜（15,360 DOF 實測 1.1 ms，是 solve 的 23%，O(構件數) 線性可平行），而且只需要回收**可見範圍**的構件。

同一 tier 的 8 次記錄 p95 散佈在 33.0–75.6 ms，其中一次 FAIL。**引用單一數字時要同時引用散佈。**
