## A · 已確認並修正

### A-1 · 中性軸符號相反（#15.6）🔴

沿 `TOP_Y` 方向 `σ(y) = axial + bendY·(y/cz)`，零點在

```
y₀ = −cz · (σ_top + σ_bot) / (σ_top − σ_bot)
```

程式少了那個負號。**純彎曲時 `σ_top + σ_bot = 0`，兩種寫法都給 0**，所以懸臂測試看不到；
唯一相關的測試只驗 `|naY| > 1e-3`，**符號錯照樣通過**。

實測（懸臂 + 400 kN 軸壓）：正確值 `+41.2524 mm`（形心**上方**，靠拉側），錯的版本會畫到
下方。**畫錯邊的中性軸比不畫更糟**，因為它看起來很權威。

已修正，並把測試換成帶號 oracle + 物理方向斷言（`compression axial puts the NA above the centroid`）。

### A-2 · 構件中間的荷載被靜默丟棄（#14）🔴

`nodeId.find(...) == end` 時直接 `continue`，回覆仍是 `ok:true`。

**這是靜默地把結構報得比實際更安全**，是這個程式能犯的最嚴重的錯。已改為
**fail-closed**：整筆請求拒絕，錯誤訊息指名座標。

正解是在荷載點切構件或改用 member load，兩者都還沒有；在那之前拒絕比猜測誠實。

### A-3 · D/C 只看兩端（#14）🔴

`ElasticAllowable` 只在 `endI` / `endJ` 上跑。控制斷面在中間的構件會被報成幾乎沒受力。

已改為**沿 stations 檢查**，並額外插入彎矩的**解析極值站**：

```
M(x) = M_i(1−t) + M_j·t + (w/2)·x(L−x)   →   x* = L/2 + (M_j − M_i)/(wL)
```

新 fixture C8 直接製造這個情況：懸臂加**向上**端點荷載 `P = wL/2`，兩端彎矩恰為零、
跨中 `wL²/8`。實測跨中 `9.24102 MPa`，對閉合解 `rel = 0`，D/C 從內部站取得。

> **過程中發現的真實限制**：原本想用兩端支承的簡支梁，但支承是 `fixAll` 而節點只在
> run 端點產生，所以兩節點構件的自由度是零，引擎正確地回報 `fully constrained`。
> **這條寫進 README 的已知邊界，沒有繞過去。**

### A-4 · run 只比材料，斷面改變被吃掉（#13.1）

一根 200×400 中途變成 100×200，整根仍以 200×400 求解，`ok:true`。

已修正。但**不是**直接把斷面加進 run 連續條件——那會讓兩段不相接，遠端變成機構。
正確做法是**斷面改變處成為節點**，走既有的分段機制（分段共用邊界方塊），構件因此
分段但仍連續。邊界方塊落在哪一段是 1 m 網格的真實近似，寫在程式註解裡而不是藏起來。

### A-5 · 斷面 token 說謊（#13.5）

`steel_h400` 是 `Section::Rectangular(200,400)`，不是 H 型鋼；`rc_400x600` 是純混凝土矩形，
不是 RC 複合斷面。同深度的 H 型鋼 `Iz`、`Iy`、自重全都不同。

**這種 token 會通過所有測試，因為測試也用同一個 token。** 已全部改名：

| 舊 | 新 |
|---|---|
| `steel_h400` | `steel_rect_200x400` |
| `steel_h300` | `steel_rect_150x300` |
| `steel_h200` | `steel_rect_100x200` |
| `rc_400x600` | `concrete_rect_400x600` |
| `rebar_d25` | `rebar_round_d25` |

舊 token 現在會被**拒絕**，不是靜默解析成別的東西。

### A-6 · 輸入 fail-open（#18）

缺 `mat` → 預設 steel、缺 `section` → 預設 `steel_h400`、任意 double 截成 int、重複座標
後蓋前、缺 `revision` → 0。**每一條都把壞請求變成另一個可以求解的結構，而且回覆說 ok。**

全部改成 fail-closed，各有一個測試（C9 九項）。`revision` 額外要求是非負整數——
它是唯一擋住過期結果造成傷害的機制，值本身悄悄變了就全垮了。

### A-7 · `mode` 這個名字會誤導下游（#16）

已改名 `governingFibre`，並補 `governingStation`。它是**控制纖維**，不是荷載型別，
**也不是產品失效事件**。

`failureType`（NONE / FRACTURE / CRUSHING / MECHANISM）與 `handoffType` **刻意不輸出**——
這裡沒有任何東西在決定它們，**缺席比猜測安全**。Java 端型別同步改名
`FailMode` → `GoverningFibre`。

### A-8 · gate 太鬆（#15.1、#15.2）

兩處已收緊：

- D/C 原本接受 strong **或** weak 軸任一答案 → 這種 gate **無法偵測軸對調**，正是
  非正方形 fixture 規則存在的唯一理由。改成只接受 strong 軸，並額外斷言兩軸的值真的不同。
- 11 站原本只核對根部與自由端 → 九個內站可錯仍 `ALL PASS`。改成**逐站**對閉合解，
  實測 `worst rel = 1.69e-16`。

> **關於上一版的說法**：`ENGINE_FINDINGS.md` 那張 11 站表格當時是**印出來的**，不是
> 斷言出來的。數字沒有錯，但「全站機器精度」這個宣稱當時**沒有 gate 撐著**。現在有了。

## C · 一處補充而非同意

#18 說「非有限 solver output 不得靜默寫成 `null`」。

`json.hpp` 把非有限 double 寫成 `null` 的**理由仍然成立**：JSON 沒有 NaN，寫出裸 `nan`
token 會讓對端整行解析失敗，把一個壞數字升級成一則丟失的訊息。

但審核的**意圖**是對的——非有限值不該被當成正常結果送出去。正確做法是在**送出之前**
偵測並回 fail-closed error，而不是改寫 writer。**這一刀沒做**，記在這裡。
