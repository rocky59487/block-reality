## §2 · v0.3a 新程式碼需要修的（v0.3b）

按修正成本排序。

### 2-1 🔴 一個引號讓世界載不進去，而且每次 chunk load 再炸一次

`SidecarLocator.java:43`、`:50`、`:83` 的 `Path.of` 全無防護。**我自己跑的**：

```
Path.of("\"C:/tmp/x.exe\"")  → InvalidPathException: Illegal char <"> at index 0
Path.of("C:/tmp/x.exe ")     → InvalidPathException: Trailing char < >
```

**那正是 Windows 檔案總管「複製路徑」給你的字串**，也是玩家填 `sidecarPath` 最自然的動作。
`InvalidPathException` 是 unchecked → `locate()` 不接 → `StructureManager` 建構子（`:109`）不接 →
`computeIfAbsent`（`:352`）不接 → `@SubscribeEvent onChunkLoad`（`:349`）不接 → **server thread 崩**。
而 `computeIfAbsent` 拋例外**不留 mapping ⇒ 每次 chunk load 再炸一次**。
`:83` 更糟——**帶引號的 PATH 項目在 Windows 上合法，那不是玩家的錯字**。

修法：包一個 `parse(String, List<String> tried)`，catch 後記一行並比照「不可用」處理；PATH 迴圈 `continue`；順手 strip 並剝成對引號。

### 2-2 🔴 解包失敗 → 靜默改跑 v0.2a 那顆舊引擎，log 一個字都不說

`SidecarLocator.java:64-66` + `:137-138`。**整個排序設計就是為了防這件事**（D-027 §3、README:106-109）。
解包失敗（防毒隔離、game dir 唯讀、磁碟滿、chmod 失敗、跨 process 撞 `.part`）→ 一路掉到 `<gd>/br-sidecar.exe`。
那是**不同位元組**的舊引擎，而 `EngineCatalogue.SUPPORTED_PROTOCOL = 1` 自最初 commit 從未變過 → 握手放行。
`describe()` 的 found 分支**整份 `tried` 直接丟棄**，所以 log／`/br status`／HUD 全部只印 `engine: <路徑>`。

順帶消失的還有「unpacked the bundled engine to …(4108756 bytes, sha256 14880e82b9aa)」——**v0.3a 最重要的一次性事件，log 裡一個字都沒有**。

修法：`describe()` 的 found 分支也印 `tried`（至少 `bundled:` 開頭那些）；bundled 失敗後若最終落在 game dir/PATH 就打 WARN；
`/br status` 加一行 `source:` 與實際檔案的 sha12。

### 2-3 manifest 的檔名欄位是未經檢查的路徑元件（等價 zip slip）

`BundledEngine.java:118`（`f[2]` **完全沒驗**，只有 `f[3]` 轉小寫、`f[4]` parse 加範圍檢查）、
`:163` `root.resolve(shortHash).resolve(e.fileName())`、`:213` `createDirectories(target.getParent())` 照建。
`Path.resolve` 遇絕對路徑會**丟棄 root**。代理實跑寫出了 `../../../../n1-TRAVERSED-relative.txt` 與 `C:/tmp/n1/N1-TRAVERSED-absolute.txt`。

**嚴重度要說準**：這需要一顆被改過的 jar，而能改 jar 的人本來就能執行任意 Java——**不是相對於惡意 jar 的提權**。它的意義是三件事：
(a) 否證了約束 3「玩家自己放的二進位永遠不會被碰」，那是寫給平台審核者看的保證；
(b) 把攻擊門檻從「重編 Java」降到「`zip -u` 改一行文字檔」；
(c) 攻擊面**不是 zip entry 名稱**——程式從不列舉 zip 目錄，manifest 才是入口，**一般的 zip-slip 檢查工具掃不到**。

修法：`parse` 對 `f[2]` 加一行 `Path.of(f[2]).getNameCount() == 1` 且不含 `/ \ : ..`；`targetFor` 加 `startsWith(root.normalize())` 保險。

### 2-4 固定的 `.part` 名 +「驗來源、搬目的」= 把別人寫到一半的檔案 rename 成 target 並宣告雜湊正確

`:214`（`resolveSibling(name + ".part")` 固定名，無 PID 無亂數）、`:253-271`（digest 掛**來源 stream**）、`:275`（`move` 搬的是**當下**在那路徑上的東西）。

代理的決定性重現：`ensure` 回傳的路徑當下是 **1,343,488 bytes / sha 4303e875…**，log 卻寫「2671944 bytes, sha256 96ce970e99f3」。
自然重現：150 輪 × 8 執行緒 → **1049/1200 失敗（87%）**，最小回傳 2,637,824 bytes。

**可達性誠實說**：單一 JVM 內 `bundled()` 用 volatile + synchronized memo 成一次，出貨路徑打不到。
打得到的是**跨 process 共用同一個 gamedir**：同資料夾同時跑 client 與 server（repo 根目錄就有 `run.bat`/`run.sh`）、
面板重啟時舊 process 未死、gamedir 在 SMB/NFS 上。**BundledEngine 自己零保護，安全網完全長在呼叫端。**

順帶：javadoc `:250-251` 寫「The check is on the bytes actually written」——**寫反了**，算的是來源 stream。

修法：**move 之後對 target 再 sha256 一次才回傳**（最便宜，同時修掉 javadoc 那條）；或 `createTempFile` 讓每個 process 有自己的暫存名。

### 2-6 Linux 上 chmod 失效會靜默關掉分析，而**沒有任何測試讀過檔案權限**

`BundledEngine.java:282-297`。我精確核過：`BundledEngineTest` 對 `posix|permission|chmod|isExecutable` **0 命中**

### 2-9 `dist/` 的多餘檔案會被打包公開，兩道 gate 都看不見

`release.yml:44-45` 與 `:114`。`sha256sum -c` 只驗**列在清單上**的檔案；`zip -q -r "../$name" . -x '*.zip'` **遞迴打包整個目錄、無白名單、含 dotfile**。
`dist/` 是追蹤目錄，一個誤 commit 的檔案就會公開出貨且全綠。
代理實測：放 `.env`（`AWS_SECRET=hunter2`）與 `br-sidecar.debug` → `sha256sum -c` **EXIT=0**；真 `zip` 產物 **10 files，兩個都在裡面，STEP-EXIT=0**。

修法：打包前 `diff <(cd dist && find . -type f -printf '%P\n' | grep -v '^SHA256SUMS.txt$' | sort) <(awk '{print $2}' dist/SHA256SUMS.txt | sort)`，不一致即 exit 1。

### 2-10 其餘 v0.3a 新碼（medium）

## §4 · gate 覆蓋的結構性問題

**251 條 gate 全過，而 §3 的五條阻擋全在。** 這不是巧合，是 gate 的寫法決定的：

| gate | 空白 | 漏掉的 |
|---|---|---|
| `J1` | 用 3 格磚墩 | §3-4 單格墊塊 |
| `J2` | 只驗 member 數量與 section 名稱，**不驗 lengthMm** | §3-2 鏡像不對稱 |
| `P2` | 只測單一全支承島、**無荷載案例** | §3-3 落地島吞荷載 |

**新 gate 是照著修好的幾何寫的。**

v0.3a 的新測試也有同一個形狀。N8 做了 36 個突變，殺掉 23（64%），**存活的都指向同一類**：

- `isGood` 拿掉雜湊只比 size → **存活**（損壞 fixture 是 11 bytes 的 `"half a file"`，正確內容 18 bytes——**光靠長度就能過**）
- `copyVerified` 雜湊只比**前 1 個十六進位字元**（4 bits）→ 存活
- 非原子寫入（拿掉 `.part` + move）→ **Windows 與 Linux 皆存活**，而 class javadoc `:38-40` 宣稱「a half-written file can never be mistaken for a good one」，**那句話的機制就是它**
- chmod 變 no-op → 存活
- prune 的 hex 過濾與長度過濾**各自都存活**（只有兩個同時拿掉才被殺；fixture 只有一個 `notahash`，任一過濾器單獨都擋得住）
- manifest 讀失敗降級成空 manifest → 存活，而降級後玩家看到「shipped: nothing」——**引擎明明在 jar 裡**

**「Gated three ways」的第三條不存在。** 全倉庫搜尋確認：**沒有任何腳本、CI job 或 make target 會「從真 jar 解出二進位 → 拿解出來的那顆跑 verify.py」**。
`GATES.md:114` 自己就標「**端到端（本輪實跑，非單元測試）**」——一次人工操作，無腳本、無 log artifact、無 evidence 條目。
而它**唯一獨有涵蓋的兩件事**，正好是完全沒有自動覆蓋的那兩項：解出來的檔可執行（§2-6）、改壞後會被換掉（只覆蓋長度改變的那半）。
**人工跑過那一次，恰好蓋住了自動化蓋不住的兩個洞——然後那一次沒有留下任何可重跑的東西。**
